## 2 被修正/撤回的旧结论

- **旧 P4.7「int8 相对 FP32 降 4.02pp、超出探索目标」撤回。** 根因是评估坐标错误:GT 在原始图像像素空间,而检测画布是 letterbox 画布,两者被混用。修复后损失为 **−0.65pp**。旧报告与失败证据全部保留,未删除、未覆盖([更正说明](../experiments/p4_ptq_eval/CORRECTION_NOTICE.md))。
- **旧 E1 之前合同 v1.2 的累加界不保守**:`127·Σ|qw|` 且 `np.abs` 对 int8 的 −128 会静默溢出回 −128。v1.3 改为逐输出通道 `B[o] = |qb[o]| + 128·Σ|qw[o,:]|`,权重先展宽 int64,越界在打包时**真实抛错**。
- **旧资源结论「两器件共用 220 DSP」撤回**,按 Zynq-7010(80 DSP,算力天花板 61.9 FPS)与 7020(220 DSP,170.1 FPS)分列;均为带假设的天花板,不是吞吐声明。

**重要方法学发现(影响今后所有验收):MinGW gcc 13.2.0 不可重复构建。** 同一源码、同一命令下连续两次编译产物哈希不同(大小恒为 85919 字节,内容有差异,疑为 PE 头时间戳/构建 ID)。因此可执行文件哈希**只能作为溯源记录,不能作为「重编成功」的判据**;判据必须是行为一致——用新二进制重跑全部 15 向量仍 15/15 逐位一致。

## 3 本轮实际修掉的缺陷(全部记录)

RTL 与测试台各修了一个会改变结论的缺陷,若只跑一次很可能被误判为通过:

1. **RTL:`in_cnt/wt_cnt/p_cnt` 只算不存。** 三个加载计数器有下一值 `*_cnt_n` 却从未写回寄存器,`in_ready` 恒真而计数恒 0,任务永远停在 LOAD_IN。测试台首次运行即卡死暴露。
2. **测试台:场景 5/6 漏 `$readmemh`**,喂入全 x;测试台自身断言(输出数量、错误码)全部通过并打印了 `TB_PASS`,**只有独立比较器发现输出全是 `xx`**。这直接印证了计划中「不能靠搜索控制台的 PASS 作为唯一验收」的要求,现已在测试台内加入输出 x 断言。

其余为运行器/表示层问题(Windows CRLF 破坏逐字节比较、iverilog 以控制台代码页打印中文路径导致解码崩溃),详见 P5 简报。

## 4 当前状态与边界(不得越界陈述)

- **可以说的**:合同域内 Python / C / RTL 三方逐位一致;最小 3×3 stride=1 pad=1 卷积在仿真中行为正确;真实层的一个受支持层已通过 RTL 逐位验收。
- **不能说的**:未综合、未做时序分析、未上板、无功耗数据、无板上 FPS。P5 的周期数是仿真测量值(真实层 2408449 周期对应单 MAC 结构),**不是性能声明**。
- 未支持配置(非 3×3、非 stride=1、超尺寸/超通道、非法移位)一律**显式拒绝**,不是「支持」。
- RTL 只验证了**一个**受支持层(`model.6.m.0.cv1`)与**一张**冻结开发图;整网 RTL 尚不存在,不能由此推断整网正确。
- 真实数据采集仍按计划推迟;软硬件默认仍是原始 FP32 128 模型,320 仍为研究候选;P3 默认规则未改。
